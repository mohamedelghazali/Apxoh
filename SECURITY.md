# Security Policy — Apxoh

## Supported Versions

| Version | Supported |
| :--- | :--- |
| `0.1.x` (pre-release) | Security fixes only |
| `< 0.1.0` | Not supported |

## Reporting a Vulnerability

**Do not** open a public GitHub issue for security vulnerabilities.

### Reporting channel

- **Email:** [m.elghazalisediki@gmail.com](mailto:m.elghazalisediki@gmail.com)

### What to include

- Description of the issue
- Reproduction steps
- Affected version(s) and commit, if known
- Potential impact (CVSS v4.0 score if possible)
- Suggested fix, if any

Do not include live credentials, private keys, or personal data in the report.

### Response targets

The following are target service levels, not guaranteed resolution deadlines.

| Severity | Acknowledgment target | Fix target |
| :--- | :--- | :--- |
| Critical | 24 hours | 7 days |
| High | 48 hours | 30 days |
| Medium | 5 days | 90 days |
| Low | 10 days | Next planned release |

Full process: see `docs/VULNERABILITY_RESPONSE.md` (draft; collaborative authoring pending).

## Scope

Covers Apxoh itself — the repository, CLI, engine, schemas, workflows, and distribution artifacts. Security issues in projects governed by Apxoh are their maintainers' responsibility unless caused by an Apxoh rule or tool.

## Out of Scope

- Vulnerabilities in third-party dependencies should also be reported upstream; Apxoh may coordinate where its use is affected.
- Vulnerabilities requiring physical access without a relevant software attack path.
- Vulnerabilities in AI model providers or third-party services outside Apxoh's control.

## Coordinated Disclosure

Apxoh will coordinate disclosure with the reporter and aims to credit reporters in release notes unless anonymity is preferred.

## Security Metadata

- Security contact: `.well-known/security.txt`
- SBOM: intended for publication with releases; implementation status must be verified per release.
- SLSA provenance: generated by the tagged-release workflow when that workflow completes successfully.
